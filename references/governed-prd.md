# 治理型 PRD

用于多团队、正式审批、合规/安全、平台级变更或需要长期追溯的项目。先按 [标准 PRD](standard-prd.md) 完成产品内容，再增加实际需要的治理信息。

## 必要治理项

### 文档控制

- PRD ID、版本、状态、创建和更新时间。
- 产品负责人、评审角色和审批状态；原材料没有时标待确认。
- 来源材料及版本，必要时记录固定链接或文件哈希。
- 替代或被替代文档的关系。

### 稳定标识与追溯

根据项目规模使用稳定 ID，例如：

- `GOAL-###`：产品目标。
- `FR-###`：功能需求。
- `AC-###`：验收条件。
- `NFR-###`：产品质量要求。
- `RISK-###`：风险。
- `DEC-###`：关键决策。

维护最小追溯关系：

| 来源 | 必须关联到 |
|---|---|
| 每项 FR | 至少一个产品目标或明确的合规/运营依据 |
| 每项复杂 FR | 至少一个可判定 AC |
| 每项 NFR | 适用范围和验证方式 |
| 每项风险 | 影响、应对方向和责任角色 |
| 每项开放问题 | 责任角色、目标决策阶段和影响 |

不设任意通用百分比。团队已有质量门时遵从团队标准；没有标准时，任何未关联需求都必须有明确原因，不能静默遗漏。

### 依赖、风险与发布

- 区分产品依赖、外部依赖和技术评估项。
- 风险记录发生条件、影响、应对方向和剩余风险。
- 发布条件描述用户和业务结果、质量门及必要审批，不替研发编工期。
- 灰度、兼容、迁移或回退影响用户时，说明用户看到什么和如何恢复；实现细节进入技术方案。

### 合规、安全与隐私

只记录适用于本项目的法规、策略和产品义务，并保留准确来源。不要根据产品类别自动推定必须满足某项法规。把用户权限、数据可见性、同意、删除、留存和审计结果写成可验证要求。

## 质量门

在声称“可评审”“可批准”或“最终版”前检查：

1. 范围、目标、用户和成功指标没有未说明的矛盾。
2. 每个 FR 都有依据和验收；每个 NFR 都有可验证结果。
3. 关键依赖、风险、权限、兼容和开放问题已经记录。
4. 所有审批状态都有来源；待审批不能写成已通过。
5. 追溯关系完整，未覆盖项有可见说明。
6. 文档版本和来源版本可识别。

未通过质量门时输出阻塞项和修订建议，不伪造通过状态。
