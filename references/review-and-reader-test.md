# PRD 评审与读者测试

## 1. 先识别评审目标

用户只要求评审时，不直接重写文档。先确认或推断评审重点：完整性、清晰度、精简度、可验收性、事实可靠性、结构、产品/技术边界或发布准备度。若用户没有指定，执行综合评审。

## 2. 综合评审维度

| 维度 | 检查内容 |
|---|---|
| 事实可靠性 | 是否把示例、推断、计划讨论或冲突材料写成已确认结论；关键数据是否有来源 |
| 问题与目标 | 问题、用户、影响和目标是否清楚；指标是否真实可测 |
| 范围 | 包含、不包含和后续内容是否可区分；是否存在隐性扩张 |
| 产品规则 | 默认状态、操作结果、数据展示、权限、边界、空值和异常是否明确 |
| 验收 | 复杂规则能否由 QA 通过可观察结果判断对错 |
| 一致性 | 名称、字段、数量、原型、状态和章节之间是否矛盾 |
| 兼容与风险 | 历史数据、旧用户、依赖、关键风险和开放问题是否按需覆盖 |
| 文档效率 | 是否存在重复、套话、实现细节或缺少必要依据 |

## 3. 评审输出

默认输出：

1. **总体判断**：适合继续共创、可进入评审、存在阻塞，或可发布。
2. **阻塞问题**：会导致范围、方案、验收或结论错误的问题。
3. **重要改进**：不阻塞但明显降低理解或执行质量的问题。
4. **轻微问题**：命名、重复、结构和表达问题。
5. **待确认清单**：问题、来源冲突和对文档的影响。
6. **建议修改顺序**：按影响和依赖排序。

每条问题引用具体章节或原文片段，说明为什么有影响，并给出修订方向。不要只给抽象评价或只报一个分数。

## 4. 精简现有 PRD

精简时保留事实、规则、依据、决策、验收和未决项。优先删除：

- 不提供新信息的背景套话。
- 同一规则的重复表述。
- 原型已清楚表达的静态布局。
- 与产品结果无关的内部实现。
- 未被材料支持、且不是明确建议的推测。

先报告计划删除或合并的内容；用户要求直接修改时再执行修改。

## 5. 独立读者测试

适用于重要 PRD 发布前。测试目标是确认没有参与共创、只看到文档的读者能否正确理解。

### 测试步骤

1. 预测 5–10 个真实读者会问的问题，覆盖范围、流程、规则、异常、指标、风险和未决项。
2. 若有独立子任务或隔离上下文能力，把“PRD 原文 + 单个问题”交给没有对话历史的评审者。
3. 记录读者回答是否正确、依据是否能在文档中定位、哪里产生歧义。
4. 额外检查隐含前提、内部矛盾、缺少定义和无法验证的词语。
5. 修正文档后重测失败问题，直到不再出现新的关键误解。

若无法创建独立上下文，生成一份“读者测试包”，包含测试问题、正确答案要点、文档依据和失败判定，供用户或后续任务执行。不得把当前对话中的隐含知识带入正确答案。
