# 模式路由

## 决策顺序

按以下顺序判断主模式：

1. 用户只要求评审、找问题、精简或发布前测试现有 PRD：选择“评审/读者测试”。
2. 项目涉及多团队、正式审批、法规/安全、平台级变更、复杂依赖或明确追溯要求：选择“治理型 PRD”。
3. 项目是新功能或中型需求，需要完整目标、范围、指标、功能规则和验收：选择“标准 PRD”。
4. 项目是已有产品的小范围界面、流程、字段或规则调整，且通常已有原型：选择“精简迭代”。
5. 材料尚少，目标是快速对齐问题、方案假设或决定是否立项：选择“需求简报”。

用户明确指定模式时遵从用户。用户提供组织模板时，选择最接近的工作流，但使用用户模板作为输出结构。

## 判断信号

| 信号 | 倾向模式 |
|---|---|
| “先写一页”“先对齐思路”“是否值得做” | 需求简报 |
| “已有原型”“小改动”“历史数据”“默认状态” | 精简迭代 |
| “新功能”“完整 PRD”“成功指标”“用户故事”“验收” | 标准 PRD |
| “跨团队”“审批”“合规”“平台迁移”“追溯矩阵” | 治理型 PRD |
| “帮我审一下”“哪里不清楚”“发布前测试”“精简现有文档” | 评审/读者测试 |

## 模式升级与降级

- 精简迭代出现跨团队依赖、重大风险或复杂权限时，升级到标准或治理型。
- 标准 PRD 若只有早期假设、没有足够问题证据，可以先降为需求简报，不伪装成最终 PRD。
- 治理型 PRD 不代表内容越多越好；只增加实际需要的治理字段和质量门。
- 评审发现文档需要大范围重构时，先提交评审结论和建议模式，得到授权后再重写。

## 组合规则

写作模式只能有一个主模式。评审/读者测试可以作为第二阶段附加：

```text
需求简报 → 决定是否进入 PRD
精简迭代 → 一致性检查
标准 PRD → 完整性评审 → 读者测试
治理型 PRD → 质量门检查 → 独立读者测试
```

不要把治理型追溯、完整市场分析和十几个固定章节强加给简单页面迭代。
