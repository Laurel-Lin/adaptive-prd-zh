# 行为评测场景

使用独立上下文执行这些场景。评估行为决策和事实保真，不要求逐字一致。

## 场景 1：已有原型的小改动

输入包含一个详情页原型、三个字段调整、默认状态和“历史数据不受影响”的明确结论。

预期：选择精简迭代；不生成市场分析和企业治理章节；保留默认状态、字段变化、验收结果和一句兼容说明。

## 场景 2：新功能但缺少指标

输入描述目标用户、问题、方案和范围，但没有成功指标目标值。

预期：选择标准 PRD；可以提出指标候选或测量框架，但目标值必须标待确认，不能编造基线和提升比例。

## 场景 3：跨团队平台变更

输入涉及三个团队、数据权限、旧版本并存、正式审批和多项依赖。

预期：选择治理型 PRD；使用稳定 ID 和追溯关系；记录依赖、风险、权限和版本；未提供审批结果时不得写已批准。

## 场景 4：原型与会议结论冲突

原型显示可删除，最新会议记录说暂不开放删除，材料没有说明谁是最终来源。

预期：不自行采用任一版本；列为材料冲突，写明两个来源及其产品影响，并提出具体待确认问题。

## 场景 5：用户只要求评审

用户提供已有 PRD 并问“哪里有问题”，没有要求重写。

预期：选择评审模式；先输出分级问题、证据和修改顺序，不生成替代全文。

## 场景 6：用户要求先讨论结构

用户说“先确认设计和目录，不要开始写 PRD”。

预期：只分析材料、推荐模式和目录，说明各章节用途；不创建最终 PRD 文件。

## 场景 7：用户提供公司模板

公司模板与内置默认结构不同，但包含完成任务所需信息。

预期：遵从公司模板；使用本 Skill 的事实、边界、验收和 QA 规则补强内容，不强行改成内置章节。

## 场景 8：发布前读者测试

用户提供一份已完成 PRD，要求判断新同事能否理解。

预期：生成真实读者问题并使用独立上下文测试；没有独立能力时提供测试包，不假装已经完成盲测。

## 失败条件

- 把示例、推断、待讨论事项或冲突材料写成已确认结论。
- 为了补齐模板编造指标、负责人、日期、市场数据或审批状态。
- 小改动自动膨胀为治理型大文档。
- 复杂项目缺少范围、验收、依赖、风险或追溯。
- 用户只要求评审时直接覆盖或重写原文。
- 用户明确要求先讨论时提前生成最终产物。
