# 共享写作规则

## 1. 事实状态

整理材料时在内部维护四类信息：

| 类型 | 定义 | 写作方式 |
|---|---|---|
| 已确认事实 | 原文、原型、数据或明确结论直接支持 | 可以直接写入正文，并在关键数据旁保留来源 |
| 合理推断 | 根据多条材料可以推出，但没有被明确确认 | 标为“推断”并说明依据；不得升级为最终规则 |
| 待确认项 | 缺少会影响范围、规则、指标或验收的信息 | 集中列出具体问题和影响，不用模糊措辞代替决策 |
| 材料冲突 | 两个可信来源描述不一致 | 并列冲突内容、各自来源和待决策人，不自行选边 |

“示例”“建议”“评审意见”“计划讨论”不等于已确认方案。作者身份、会议语气或文档位置也不能单独证明结论已经通过。

## 2. 来源与数据

- 对关键数据记录来源、统计口径、时间范围和样本范围；缺一项时说明限制。
- 对外部研究、竞品结论和标准保留可访问链接或准确出处。
- 原材料未提供目标值时，写“目标值待确认”，不要根据行业经验自动补数。
- 原材料未提供负责人、时间或审批结果时，不填入虚构占位姓名或状态。
- 可以提出建议，但必须与已确认要求分开。

## 3. 产品与技术边界

PRD 可以定义：

- 谁在什么场景使用。
- 用户可以做什么、看到什么、不能做什么。
- 默认、加载、成功、失败、空值、无权限和恢复操作。
- 数据展示、排序、归属、限制和历史兼容结果。
- 可测量的性能、安全、可访问性或合规结果。

PRD 通常不定义：

- API 顺序、请求结构、错误码、数据库表、缓存和内部对象。
- 前后端分工、事件监听、代码结构、迁移脚本和回滚实现。
- 未经研发确认的技术选型和工期。

如果技术限制会改变用户体验或范围，写产品结果和约束，并把内部方案留给技术设计文档。

## 4. 写作与结构

- 用户模板优先。没有模板时使用所选模式的默认结构。
- 一条规则只定义一次；其他位置引用或保持简短一致。
- 原型表达布局，文字补充触发条件、状态变化、限制和原型无法表达的规则。
- 一句话尽量表达一条规则。删除套话，不删除来源、依据、关键取舍和未决原因。
- 同一对象使用同一名称。字段名称以用户指定的数据标准或最新确认材料为准。
- 不机械增加权限、性能、风险等章节；只有确实相关时才写，但相关时不能省略。

## 5. 询问策略

先利用已有材料，不重复询问已回答内容。只有以下缺失会阻止可靠输出时才提问：

- 目标用户或核心问题无法识别。
- 范围存在互斥解释。
- 关键操作结果或权限边界无法判断。
- 用户要求最终版，但关键指标、验收或发布条件仍未定。

问题要集中、具体，并说明答案会改变哪一部分。其余缺失内容标为待确认后继续完成可做部分。
